# Session 7 · Drift and retraining: lab guide

Goal: measure drift on the fraud API's traffic with K-S, chi-squared and PSI, tell which drift type each test can see, and wire a drift verdict to a retraining run in GitHub Actions, only after you have diagnosed the cause.

Each step is small and ends with a **Check**. Do not skip ahead.

Deliverable: a drift-triggered retraining run visible in GitHub Actions, the drift reports of the baseline, data-drift and concept-drift runs, and a paragraph on what the retraining changed and what it did not (step 6).

Terminals: **terminal A** runs the API and stays open. **Terminal B** runs the commands of this guide.

## Part 5 · Wire the trigger (only after the diagnosis)

The exit code of `fraud.drift` is the trigger: `3` when the max PSI is above `psi_retrain` (0.25 in `params.yaml`), `0` otherwise. The trigger starts a retraining run only on `3`, and only after your diagnosis of step 4.

**5.1** Save this script as `retrain_on_drift.sh` at the root of the repository:

```bash
CURRENT=${CURRENT:-logs/drift.jsonl}
uv run python -m fraud.drift --current "$CURRENT"
code=$?
if [ "$code" -eq 3 ]; then
  psi=$(uv run python -c 'import json; print(round(json.load(open("reports/drift.json"))["max_psi"], 3))')
  gh workflow run train.yml -f reason="drift PSI $psi"
fi
```

**Check:** `bash -n retrain_on_drift.sh` prints nothing (no syntax error).

**5.2** Check that the trigger stays silent on normal traffic. Run it on the baseline:

```bash
CURRENT=logs/baseline.jsonl bash retrain_on_drift.sh
```

**Check:** the output ends with `-> ok`, and no workflow starts.

**5.3** Run the trigger on the data-drift log (the step 2 traffic, saved in `logs/drift.jsonl`):

```bash
bash retrain_on_drift.sh
```

**Check:** the output says `reason=drift PSI` followed by a value above 1, and `gh` prints that a workflow run was created.

**5.4** Watch the run:

```bash
gh run list --workflow train.yml --limit 3
gh run watch
```

**Check:** the run goes through the data, training, evaluation gate and export steps. The `publish` job then waits for approval in the `production` environment. Approve it, or leave it waiting and say so in your report.

**Note:** the `|| gh workflow run` form is not used on purpose. Chaining with `||` would start a training run on any failure of the drift command, not only on a drift verdict.

## Known limits of this lab

These limits are part of the lesson. Name them in your report.

- **Same data, same model.** The CI retraining reproduces the pipeline on the same training split, so the model comes out identical. The pipeline is proven; nothing has adapted to the drift.
- **Two registries.** The CI workflow runs MLflow with a local SQLite database on the GitHub runner (`MLFLOW_TRACKING_URI=sqlite:///mlflow.db`). The run and the `@staging` alias live on the runner, not in your local MLflow at http://localhost:5000. Evidence is the Actions summary and the `model` and `reports` artifacts.
- **The exit code says drift, not cause.** A unit bug gives the same exit code 3 (Part 4). The trigger is only as good as the diagnosis that precedes it.
- **The reference is a choice.** The reference is a healthy production window, and the training split would give a different verdict (Part 7). Choosing the reference is a decision you must state.
- **Thresholds.** `psi_alert` (0.1) and `psi_retrain` (0.25) are rules of thumb, not validated on real data. State how sensitive your verdict is to the number of bins.
